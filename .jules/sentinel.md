## 2025-03-06 - [Hardcoded Admin Credentials]
**Vulnerability:** Found hardcoded super admin credentials in `src/contexts/AdminContext.tsx`. The credentials (`SUPER_ADMIN_USER = "muhammadsolih"` and `SUPER_ADMIN_PASS = "muhammadsolih2234"`) are explicitly stored in the client-side code.
**Learning:** In a pure frontend application, any hardcoded credentials can be easily read by anyone inspecting the code or the bundled JavaScript files. This grants unauthorized full admin access to the application, bypassing all intended security controls.
**Prevention:** Never hardcode credentials or secrets in the client-side code. Use environment variables (e.g., `import.meta.env.VITE_SUPER_ADMIN_USER`) during the build process, or implement a proper backend service for authentication where secrets remain on the server.

## 2025-03-06 - [Plaintext Passwords in Client Storage]
**Vulnerability:** Found that user passwords were saved in plaintext within `localStorage` in the mocked frontend implementation (`AuthContext.tsx`). This exposes credentials to XSS attacks or anyone with physical access to the device.
**Learning:** In purely frontend architectures where data is mocked and stored locally, saving sensitive data like passwords as plaintext is a high-risk practice. Even for a mocked frontend, proper hashing (e.g., using the Web Crypto API PBKDF2) prevents exposing credentials in client bundles and client storage. Falsy validation checks on password fields also need to be avoided, as they can break legitimate empty strings for OAuth providers.
**Prevention:** Always hash passwords before storing them. Use standard key derivation functions such as PBKDF2 with a random salt via `crypto.subtle`. Prevent account enumeration vulnerabilities by ensuring generic login error messages that do not reveal whether the email exists.
